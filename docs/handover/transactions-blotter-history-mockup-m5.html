M-5 design notes — checkpoint decisions and what the 2026-09-07 snapshot pins

Decision 1 · OP-10 — indicator placement (ADR-0128 Q-2, ADR-0130)

  • Candidate A: cash position detail page, under the inv-header, above Positions (frame 2). Candidate B: Transactions-area banner between the area header and the first section (frame 1). C: both. Toggle "Indicator placement".
  • Derivation is live: holdings_as_of(txns, today) for the balance, first_negative_holding_date(txns) for "since" — both pure in services/investments/holdings.py. No stored flag, no acknowledgement, no schema; absent (not struck through) at ≥ 0 — toggle "all ≥ 0".
  • Multi-currency: one line per negative cash position (toggle "two negative"); each line links to its detail page. The banner names positions, never sums across currencies (ADR-0099 seam).
  • Copy: the second sentence is MD-9's flag-notice copy verbatim; the first restates the confirmation panel's line in present tense. "Last taken below zero by ticket #n" is a copy proposal — it needs a read of the most recent ticket-emitted transaction on the position; drop it if the derivation should stay purely ledger-side. MC lean: C (both) — the banner is where the operator who caused it is; the detail page is where the position is looked at later.
  • Never blocks anything: the indicator is informational on every surface (ADR-0130); no gesture lives on it.

Decision 2 · OP-25 — resume mechanism

  • The row's Open gesture is agnostic (one button, one hx-get). Two candidates: (a) five per-flow GETs each accepting ticket_id, or (b) one GET /api/transactions/ticket/{id} that consults _FLOWS and renders the right composer.
  • Snapshot facts: the wizard already resumes via GET /api/transactions/wizard?ticket_id= (S4b, _resume_step); the other four opening GETs take no ticket. _composer_context(..., ticket=, flow=) already accepts a ticket; _form_from_ticket is written for the wizard's payload and must be checked for the four single-page shapes (a GET-side helper, not a composer change — if it turns out to need one, STOP per kickoff).
  • A ticket row stores kind/direction/investment_id/master_data, not a flow. The single GET needs a reverse lookup _flow_of(ticket) (kind, direction, is_investment_creating) → _FLOWS key, in one place; the blotter's "Flow" column label comes off the same lookup (a label field added to _Flow). MC lean: (b), single GET; the wizard GET stays and the single GET delegates to it for U-NEW.
  • Open on a proposed/approved ticket renders read-only with Book now / Cancel (the composer already renders non-draft tickets as records — see get_wizard docstring).

Decision 3 · Cancel / Reverse home

  • Three candidates, toggle "Cancel / Reverse home": row ⋯ menu (blotter and history), opened composer header, history detail footer. Reason capture is an inline panel under the row (no modal), with the service rule surfaced: required for proposed/approved (CANCEL_REASON_REQUIRED_STATUSES), optional for draft, always for reverse. Draft wording "Discard draft" vs "Cancel ticket" — copy proposal, D-register.
  • 3a · Blocked rendering: str(exc) verbatim as the red block (A-7), five causes shown via the outcome toggle. Sub-decision 3d: the sentences carry raw row UUIDs — accept, or allow an additive resolved-name line beneath.
  • 3b · ReversalReport: green done-block with count by effect type (from reversed, grouped), then the retained-shell consequence block rendering shell.retained_because verbatim after "Investment retained, inactive — because:".
  • 3c · Actor: there is no cancelled_by column; set_status receives the actor but writes none for cancelled. AuditLogRepository exposes only has_update_since; showing the cancel/reverse actor means one new read-only method (e.g. actor_of_update(table, record_id, new_status)) reading audit_logs.user_id where new_data->>'status'='cancelled'. Toggle "Actor on history": station columns only (proposed_by/approved_by/booked_by via UserRepository, the Cases _resolve_owner_names precedent) · plus audit-derived cancel actor · none. MC lean: station columns in P-5b; audit-derived actor is a separable concern — decide now whether it is in P-5b or parked.
  • Reverse is offered only where status='booked'; a cancelled/reversed row has no mutation. Both live under require_role("owner") + verify_csrf.

Decision 4 · OP-22 visibility

  • Toggle "OP-22 hint". Two candidate positions: a one-line hint above the blotter table, and a third line inside the detail indicator. Either both, one, or documentation only. If shown, the wording is a copy proposal for the D-register (no mockup anchor).

Decision 5 · History filter set v1

  • Status is given (all / booked / cancelled / reversed — "reversed" is cancelled AND booked_at IS NOT NULL, so it is a derived option on the same column). Candidates: kind, investment, trade-date range, free text over note/cancel_reason. Toggle "History filters v1".
  • Repository: list_by_status(statuses) exists; the prompt adds read-only keyword parameters to it (or a sibling) for exactly the chosen set — nothing speculative. Free text is the only candidate that needs an ILIKE and is the one MC would drop from v1. MC lean: kind + investment + date range; no free text.
  • Ordering stays ticket_number DESC. No pagination in v1 unless the operator wants it (would be a limit/offset pair, still read-only).

Pinned, not for decision

  • Effects grouped by effect_type via the existing _effect_rows shapes (P-4b); rows whose target is gone render "This row is no longer in the book" — after a reversal every row of that ticket does, which is correct and is what history is for.
  • Blotter columns: ticket #, flow label (from _FLOWS), investment or "creating: name", amount, trade date, status chip with station actor/date. Amount for a draft without figures is "—". The section_pill="S5" and both placeholder sentences retire with P-5a/P-5b.
  • No migration, no index. No four-eyes gesture. No composer behaviour change.

{# The hypothetical-transaction entry form (mockup ④, ADR-0104 §2/§7). Its own partial, because it renders in two places: inside the Cash Flow Planning section, and inside the error partial when a submission was refused — where it comes back **open**, holding what the operator typed, beside the reason the plan world would not carry it. The field shape is the actual-entry form's (`web/templates/investments/_position_form.html`), and deliberately so: the two describe a transaction the same way (ADR-0104 §2). What differs is where the entry goes — D21: actuals on the investment detail page, hypotheticals only here, into the parameter set, never into `position_transactions`. Three rules the form states and the server enforces: * **The sign is typed, never derived** (ADR-0097 §2, as on the actual form): positive units for a buy, negative for a sell. * **The currency is not a choice.** It is the selected investment's, bound to the selection by the script below and rendered read-only — which is what makes a `CurrencyMismatchError` unreachable from this surface. * **The date floor is the seam plus a day.** `t₀` itself is realised history, and an overlay never touches it (ADR-0104 §5). Submission is the slider's idiom: an HTMX GET that re-issues the **whole** parameter set (`hyp.base_query`) and lets the form's own fields append the entry beside it. The server merges the two and re-emits the canonical `t{n}_…` encoding — the UI never formats an overlay key. Context: `hyp` (from web/routes/planning_desk.py, `_build_hyp_context`) and `section_url`. #}

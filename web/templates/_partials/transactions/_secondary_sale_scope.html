{# MD-18's scope control (M-3, "Scope of the sale"). Two options, and the second one refuses. It is offered rather than hidden because MD-18's answer is a *reason*, not an absence: an operator who came here to record a partial sale needs to be told why they cannot, and what to do instead — which the red note below the form then says. Out of band, like the context strip and the message panel, because the option states are derived: which one carries `is-selected` and which one `is-refused` is the server's answer to what was posted, and the block sits above the static Proceeds inputs that a recalculation must not disturb. Since P-UX-A1b2 each option is a `pf-choice`, the family the settlement candidates already use, with its own `.is-selected`. `is-refused` has no counterpart in the record — no mock offers a choice that refuses — so it stays a state class beside `pf-choice` and its one border rule is scoped to this Area in components/transactions.css. Both radios carry a stable id, which is what lets the selection survive the swap: htmx restores focus to the element with the same id afterwards. Context: partial_sale, oob. #}
